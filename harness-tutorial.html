Harness engineering for the SDLC

A harness is everything around an AI agent that makes its work reliable: the instructions it reads, the files it can find, the checks its output must pass and the feedback it gets. Harness engineering is the job of designing that environment, so that people steer and agents execute.

OpenAI described the idea in Harness engineering: leveraging Codex in an agent-first world. A small team shipped a product in which agents wrote nearly all of the code. Their effort moved from writing code to building the scaffolding that let agents work well. The lessons that matter most for this playbook:

Give agents a map, not a manual

A short AGENTS.md (about 100 lines) points to deeper docs. One giant instruction file crowds out the task and goes stale.

The repository is the system of record

Specs, plans, decisions and quality scores live as versioned files in docs/. Anything an agent can't see in the repo doesn't exist for it.

Enforce rules mechanically

Architecture and taste are encoded as linters, structural tests and CI gates, so a rule holds on every run, not only when someone remembers it.

Plans are first-class artifacts

Execution plans with progress and decision logs are checked in (docs/exec-plans/active, completed, tech-debt-tracker.md).

Fight entropy continuously

Agents copy whatever patterns exist, good or bad. Recurring clean-up, doc gardening and quality scores keep drift small.

Humans steer, agents execute

People set intent, review decisions and approve outputs. Agents do the producing, inside guardrails.

What this playbook adds

The OpenAI write-up is about one engineering team. This playbook applies the same principles across a whole delivery lifecycle in which product managers, designers, solution / data / integration architects, engineers, QA and SRE each have their own agents. Three properties make the output deterministic:

  • One skill, one artifact, one template. Every skill writes exactly one document from a fixed markdown template, with fixed section ids and table columns, so outputs look the same on every run and can be checked by code.
  • Gates before approval. Blocking checks (schema valid, traceability, template conformance, OpenAPI lint, contract tests, etc.) run before a person approves the artifact.
  • Events drive the next step. An approved artifact emits an event (prd.approved). Skills subscribe to events, so the workflow is a graph you can read, not a chain of chat prompts.

Every approved artifact is also written to a common knowledge graph, so any agent can ask "which stories implement REQ-03 and which tests verify them?" without rereading every document.

  "status": "produced", "openQuestions": [], "next": ["TD-01", "SA-01"]
}

Key design decisions drive the design

The Solution Architect's /decide-key-design skill scores every option 1–5 on product priority, engineering effort and ops TCO over 3 years (default weights 35 / 30 / 35). The chosen option feeds the solution architecture. When the chosen option deviates from a standard, the KDD records a dispensation (DSP-nn) and /raise-tech-debt opens a Jira ticket, reviewed by the Product Owner and the Lead Solution Architect, so the compromise is paid back later.

4Create agents and skills

Worked example: a retail team adds product-search indexing to the Engineering team.

  1. Open the persona. In Playbooks, choose a persona in the sidebar, or click + New persona (Team: Engineering, Name: Search Engineer, Accountable: Search Engineering Manager).
  2. Add the agent. Click + Agent. Name it in kebab-case (search-agent), pin the model, list the Claude Code tools (Read, Write, Edit, Bash, Grep) and MCP servers (graph-memory). The name becomes .claude/agents/search-agent.md.
  3. Add the artifact first, or from inside the skill form. Click + Artifact:

  4. Add the skill. Template syntax

Each line in an artifact's Template field is one section, in order. Traceability, Open Questions and Approvals are added at the end automatically.

h: introduction | Introduction | What the index serves and which stories need it
t: fields | Indexed Fields | Field; Source attribute; Type; Analyzer; Facet (Y / N)
t: queries | Query Patterns | Query; STY refs; Boost; p95 ms
c: definition | Index definition | json

h: is a prose section (<h2 id="introduction_details">), t: is a table with fixed columns (<div id="fields_table" data-columns>), and c: is a code block in a given format (<div id="definition_block" data-format="json">). This matches the style of prod_business_requirement_document.md. All 40 generated templates are in samples/artifact-templates/.

Graph mapping syntax

The Memory field says which nodes and edges an approved artifact writes. Clauses are separated by ;:

Node(ID-pattern) -RELATION-> Node(ID-pattern) {edge or node properties}

Story(STY-nn) -IMPLEMENTS-> Requirement {channel}; Story -PART_OF-> Epic

The playbook builds the graph schema from these clauses (Graph memory → schema, and docs/generated/graph-memory-schema.md in the scaffold).

Editing an existing skill

Click ✎ Edit on any skill card. Renaming an ID updates every reference (inputs, outputs, gates). The editor won't let two skills produce the same artifact, and won't delete an artifact that a skill still reads. Changes to a skill's inputs or gates show up in its SKILL.md, in docs/generated/workflow.md and in the upstream skills' "next" lists the next time you run the scaffold.

5Run a work item (manual mode)

  1. Create the work item. In Run, click + Work item and paste the business request. This seeds A-REQUEST and fires request.created.
  2. Start a ready skill. Ready skills are those whose input events have all fired. Click Prompt to copy a complete prompt: the inputs pinned to their versions, the template to fill, the gates and the envelope to return.
  3. Produce the artifact in Claude Code. Run the skill (/frame-opportunity WI-101) in your repository. The agent writes the document and returns the envelope.
  4. Record and check. Paste the document path and version into the step, tick each gate as it passes (or paste the envelope), and send it for approval.
  5. Approve. Each required role approves. When the last approval is in, the artifact's event fires, MEM-01 queues the graph update, and once memory.synced fires the downstream skills become ready.
  6. Reopen when something changes. Reopening an approved step marks every downstream step stale and queues a graph retract, so nothing is built on a superseded version.
Export ⤓ Work items (runs and event log) and ⤓ Memory (graph ops and state) to keep a record that you can reload later or share with the team.

6Scaffold the repository in Claude Code

The scaffold turns the master data into the files Claude Code reads: subagents, skills, templates, the map and the docs layout.

1. Generate the files

In the playbook, open Orchestration → Repository scaffold and click ⤓ Scaffold .sh. Run it at the root of your repository:

# commit first: generated files are overwritten (CLAUDE.md and the tech-debt tracker are kept)
git add -A && git commit -m "Before harness scaffold"
bash scaffold-harness.sh
git status

You get this layout, which follows the OpenAI harness structure plus folders for quality, reliability and graph memory:

├── exec-plans/active/ completed/ tech-debt-tracker.md

2. How Claude Code uses each file

FileRead by Claude Code as
CLAUDE.mdProject memory, loaded at the start of every session. It imports @AGENTS.md, so Claude Code and other agents share one map.
.claude/agents/<name>.mdA subagent with its own system prompt, tools and model. List them with /agents. Claude delegates to one when a task matches its description, or you ask for it by name.
.claude/skills/<skill>/SKILL.mdA skill. Run it as a slash command (/write-prd WI-101), or Claude loads it when the request matches its description. It lists the inputs, graph memory use, steps, output contract and gates.
templates/artifacts/Copied by the skill to the document path, then filled in. Section ids and columns must stay.
docs/generated/*Read-only context: which event triggers which skill, the graph schema, the machine-readable workflow.

3. Run your first skills

cd your-repo && claude

# inside Claude Code

/frame-opportunity WI-101                # reads docs/product-specs/WI-101/00-request.md, writes 01-brief.md

Record each envelope in the playbook's Run tab and approve there. That keeps triggering manual and visible while you build trust in the skills.

4. Optional: check templates automatically with a hook

A PostToolUse hook runs after Claude writes or edits a file. Exit code 2 sends the error back to Claude so it fixes the document straight away. Drafts are skipped.

// scripts/harness-template-hook.mjs
import { readFileSync } from "node:fs";
import { execFileSync } from "node:child_process";
const input = JSON.parse(readFileSync(0, "utf8"));
const file = input.tool_input?.file_path || "";
if (!/(^|\/)docs\/.+\.md$/.test(file)) process.exit(0);
const text = readFileSync(file, "utf8"), tpl = (text.match(/^template:\s*(\S+)/m) || [])[1];
if (!tpl || /^status:\s*draft/m.test(text)) process.exit(0);
try { execFileSync("node", ["scripts/harness-template-check.mjs", file, tpl], { stdio: "pipe" }); }
catch (e) { process.stderr.write(String(e.stderr || e.message)); process.exit(2); }
// .claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      { "matcher": "Write|Edit", "hooks": [ { "type": "command", "command": "node scripts/harness-template-hook.mjs" } ] }
    ]
  }
}

5. Give agents the graph memory

Every SKILL.md tells the agent to query the graph memory read-only. Start simple and grow:

  • Files first. Keep the merged graph at docs/generated/memory/<WI>/graph.json, as in the sample. Agents read it with their normal file tools.
  • A graph database later. Load the deltas into a graph store (for example Neo4j) and expose it through an MCP server registered as graph-memory, read-only for every agent except memory-steward-agent. Add it with claude mcp add or a checked-in .mcp.json.

6. Later: run without a person clicking

The same files work headless. Phase 1 of the recommended orchestration is GitHub Actions calling Claude Code in print mode when an event fires:

claude -p "Run the write-prd skill for WI-101 and finish with the harness/v1 envelope" --output-format json

Phase 2 moves the event routing into a durable workflow engine (Temporal with the Claude Agent SDK), driven by docs/generated/harness.workflow.json. See Orchestration in the playbook.

Never edit docs/generated/, templates/ or .claude/ by hand. They're generated from the master data. Change the playbook, export, and run the scaffold again; it marks new and changed files with ●.

7The knowledge graph

The common graph memory is how agents share context across personas without passing whole documents around.

How artifacts become graph

1 · Artifact approvede.g. A-STORIES v1
→
2 · Upsert queuedwith provenance A-STORIES@1
→
3 · MEM-01 extractsnodes and edges per the Memory clauses
→
4 · G-GRAPHendpoints exist, IDs valid, single writer
→
5 · Delta mergeddocs/generated/memory/<WI>/
→
6 · memory.synceddownstream skills may start
  • Single writer. Only the memory steward (/sync-graph-memory, a hook on every approval) writes the graph. Other agents read it.
  • Provenance on everything. Each node and edge records the artifact version that wrote it, so a question can always be answered from the source document.
  • Retract on reopen. Reopening an artifact retracts what it wrote and marks dependants stale. A new version supersedes the old one.
  • Documents stay the source of truth. The graph is an index for finding context. Skills still read their pinned input documents.

8Graph visualiser

The visualiser is a tab in the playbook: harness-engineering.html → Knowledge graph.

Explore the graph memory of a work item

  • Sources: the sample WI-101, the playbook catalog (personas, agents, skills, artifacts, gates), or any graph.json. It also reads the format used by the harness-engineering.ai knowledge graph.
  • Color Mode: by entity type, by team or by community (Louvain). The left panel filters each group; double-click shows only that group.
  • 2D / 3D, Search nodes, and Artifact nodes to show which document wrote each node.
  • Node details: properties, degree and betweenness centrality, community, relationships and mentions (the artifacts that wrote or reference the node, linked to their documents).
  • Trace up / Impact: follow what a node traces to, or what depends on it. Impact lists the artifacts that would go stale if the node changed.
  • Replay: the timeline rebuilds the graph in approval order, from the request to the outcome review.

10Next steps

  1. Open the playbook, click Load example, and adapt the personas and skills to your teams.
  2. Export the master data and run the scaffold in a trial repository. Run three or four skills by hand and compare the documents with the WI-101 samples.
  3. Tighten the templates and gates wherever outputs vary between runs. Every variation you remove makes the harness more deterministic.
  4. When the manual flow is stable, move the triggers to GitHub Actions, and later to a workflow engine.
