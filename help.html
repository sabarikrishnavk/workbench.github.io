FedGQL Migration Workbench — Help

Browser-only tools for moving a monolithic GraphQL schema (the MonoGraph) and BFF REST APIs onto a federated GraphQL supergraph. Every tool reads and writes the same Excel workbook, GQLRegistry.xlsx. Nothing is uploaded: files are read in your browser and your work is cached in the browser's local storage.

Quick start — end to end

  1. Start a registryOpen the Registry workbench. Click Load .xlsx to open your team's GQLRegistry.xlsx. Or click Template for an empty workbook, or Load example for the retail sample.
  2. Register the target entitiesOn the Entities sheet, add one row per entity you will migrate. Fill in its domain, business application (this becomes its subgraph) and capability, then add LeanIX / Confluence / ER links.
  3. Export the workbookClick Export .xlsx, or Save & push to share it through SharePoint or Google Drive.
  4. Generate a subgraphOpen GQL migration. On Load data, load the workbook, pick the GQL Registry entity, and Import OpenAPI spec for that entity's service.
  5. Review against the MonoGraphOptionally load the MonoGraph SDL on MonoGraph schema, browse its types and methods, and assign each to a target domain and entity.
  6. Edit and proposeOn FedGQL subgraph, edit the generated rows and fix any standards issues. Then set Approval to Proposed on each row that is ready.
  7. Copy to the registryClick Copy to GQL Registry →. Proposed rows are validated and merged into the registry on the GQL Registry tab. Or use Export subgraph xls to hand the rows over as a file.
  8. ApproveIn the Registry workbench, reviewers change Proposed to Approved, add auth scopes, then export or push the new workbook version.
  9. Migrate the codeOpen Code migration. Load the approved registry and the REST/BFF spec, map each endpoint to its FedGQL operations, and copy the generated client or server code.

Try it with the samples

Fastest route: click Load example in GQL migration or Code migration. It loads these files for you when the pages are served over http(s). The samples/ folder holds a complete retail example with seven subgraphs: product, pnp (pricing), inventory, search, cart, payments and checkout.

  1. RegistryIn the workbench click Load example, or Load .xlsx → samples/GQLRegistry-sample.xlsx.
  2. MonoGraphIn GQL migration, go to MonoGraph schema → Choose file… → samples/mono-graph.gql.
  3. A subgraphOn Load data, load samples/GQLRegistry-sample.xlsx and pick ENT-002 · ProductStoreContext. Then Import OpenAPI spec → samples/subgraph/pnp/openapi.yaml. Compare the result with the target samples/subgraph/pnp/subgraph.gql.
  4. Single-op codeIn Code migration, load the sample registry and samples/subgraph/cart/openapi.yaml. GET /carts/{id} pairs with query cart; scroll to the Sequence trace to see the router reach the product subgraph for each line.

Registry workbench workbench.html

The registry spreadsheet with a grid editor on top. Edits save automatically in the browser. The Excel workbook is the portable copy you share.

Load .xlsx header

Opens a GQLRegistry.xlsx and replaces the data in the browser.

Export .xlsx header

Downloads the registry as a new version of the loaded file (for example GQLRegistry-v3.xlsx). The export has in-cell dropdowns for Persona, Kind, Approval Status and EntityID; a value outside the list gets a warning but is kept.

Template header

Downloads an empty workbook with all five sheets and their dropdowns. It already contains the foundational FedGQL entity and its default scalar types.

Load example header

Replaces the current data with the retail sample (product, pnp, inventory and search subgraphs), the same data as samples/GQLRegistry-sample.xlsx.

Clear header

Deletes all registry data in this browser. Export first if you need to keep it.

SharePoint / Google Drive sync SharePoint | Google Drive · Pull & merge · Save & push · Settings

SharePoint | Google Drive: choose where the shared workbook lives. Each target keeps its own links and last-sync time, and the buttons act on the selected one. The page never signs in; it opens SharePoint or Drive for you to download and upload.

Settings: paste the workbook's link and the folder's link. For SharePoint that's the file and its document library. For Google Drive, use Share → Copy link on the file and on its folder; a Google Sheet link also works.

Pull & merge: download the latest workbook (for Drive, the link downloads the file directly and exports a Google Sheet as .xlsx), then select it. The workbench compares three versions: your last sync, your local edits and the shared copy. Changes from either side are merged. If a row changed on both sides, the shared version wins and your version is added as a separate “(local copy)” row, so nothing is lost.

Save & push: downloads a version-bumped workbook. Upload it to the same SharePoint or Drive folder as a new file, so the version history is kept.

Registry grid Registry tab

One tab per sheet. Every cell is editable in place, and dropdowns appear for entities (EntityID), Kind, Persona and Approval Status. Row colour follows Approval Status. Hover a column header to filter it Excel-style (▾), widen it (⤢) or hide it (×).

+ Add row

Adds a row at the top of the sheet with a generated ID (see Row IDs). If the grid is filtered to a single entity, the new row belongs to that entity.

Columns

Show or hide columns, and reset widths. Hidden columns are still saved and exported.

Sheets

Entities ID ENT-###

One row per canonical entity: Name, Experience Domain, Business Application (the subgraph it belongs to), Business Capability and Description. Everything else hangs off an entity.

Schema ID SCH-<EntityID>-###

Every GraphQL type under an entity. Kind is Key (an entity with @key), Type, Enum, Input, Interface, Scalar, Reference (a stub of another subgraph's entity) or Extend (adds fields to another subgraph's entity). Definition holds the SDL body.

Queries ID QRY-<EntityID>-###

Root Query fields. Parameters are edited one per line as name: Type. Return Type is a combo box listing the registry's types, and you can still type wrappers like [T!]!. Auth Scopes is a comma-separated list.

Mutations ID MUT-<EntityID>-###

Root Mutation fields, edited the same way as Queries. The standards prefer a single input: <Name>Input! argument.

AuthScopes ID SCP-<EntityID>-###

One row per scope and persona: pick the Persona (Customer, CustomerCare, B2BShopper, B2BShopperCare, B2BAdmin or B2BAdminCare) from the dropdown and describe the Permission it grants. If a persona has no row for a scope, it has no access to it.

Row IDs

Entities use ENT-###. Rows that belong to an entity include its ID in their own: SCH-, QRY-, MUT- and SCP-<EntityID>-<seq>, for example QRY-ENT-003-002. The migration tool generates IDs the same way. A new row starts as …-ENT-000-### (no entity yet); when you pick its Entity, the ID is renumbered under that entity. IDs you typed yourself are never changed.

Links & References and governance columns

Every sheet ends with Contacts (Domain Architect / Technical Service Owner), Approval Status (Draft → Proposed → Approved → Deprecated), Comments, Current Reference (the legacy REST or MonoGraph operation this row replaces) and Links & References.

In Links & References, each line has a type from the dropdown (LeanIX, Confluence, ER or Other) and a URL or text. ↗ opens the URL. Lines without a type are treated as Other.

Standards ⓘ and issue flags

Schema, Queries and Mutations rows are checked as you edit against the GQL Federation — Schema Standards and Patterns rules (standards.json). Flagged cells are outlined. A ⚠ badge on a row lists its issues with a fix and a link to the relevant section of the standards document. The toolbar chip filters the grid to rows with issues. Issues are advisory in the registry and never block saving.

Federated Graph

A Mermaid diagram: router → one subgraph per Business Application (or per Business Capability) → its entities, with @key fields and operation counts. Entities with the same name in different subgraphs are joined by a dashed federation edge. Copy Mermaid source copies the diagram source for docs.

Explorer

A GraphiQL-style browser for the registry's operations. Search, or filter by Queries / Mutations, then open an operation to see its auth scopes, parameters, signature, a sample operation document and the entity's SDL, each with a Copy button.

Subgraph SDL

The complete SDL a subgraph contributes for an entity: every type registered under it plus its root operations. Copy SDL copies it.

＋ Borrow / extend entity

Use an entity owned by another subgraph. Reference adds a stub (@key(…, resolvable: false)) so you can use it as a field type. Extend adds a field to it (for example, pnp adds storeContext to Product). Suggestions appear when your types already refer to another subgraph's entity.

Summary

Per-subgraph counts of keys, types, inputs, enums, scalars, queries and mutations, with an approval-status breakdown. It also shows a collapsible tree of each type's relationships; use Expand all / Collapse all.

GQL migration gql-migration.html

Migrates one registry entity at a time: its service's OpenAPI spec becomes FedGQL registry rows, which you review, propose and copy into the registry.

Load data tab

Load GQLRegistry.xlsx with Choose file…. When the pages are served over http(s), the workbook and MonoGraph schema load automatically from the same folder. Then, under Domain details, pick the GQL Registry entity you are migrating; its EntityID and domain details become the target for everything generated.

Load example header

Loads the retail sample from samples/ in one click: the registry, the MonoGraph schema, and the OpenAPI spec of the subgraph picked in the dropdown (checkout, cart, payments, product, pnp, inventory or search). It selects that subgraph's registry entity as the migration target, so the Subgraphs and FedGQL subgraph tabs are ready to explore. It replaces the cached data and mapping, and asks first. Needs the pages served over http(s); on file:// use the Choose file… buttons with the files in samples/.

Subgraph migration (.xlsx)

Optional. Reloads a …-subgraph.xlsx you exported earlier, so you can continue where you left off.

Clear cached data & mapping

Clears everything this page cached in the browser: loaded files, imported subgraphs, assignments and row edits.

Import OpenAPI spec (JSON/YAML)

Imports one spec per subgraph. Component schemas become GraphQL types, request bodies become input types, GET operations become queries and other methods become mutations. The operationId becomes the operation name. Generated rows take IDs like SCH-, QRY- and MUT-<EntityID>-### under the chosen entity.

Keys are auto-detected only from an id or <Type>Id field. For other keys (such as sku), choosing the registry entity is enough: every generated row belongs to it.

MonoGraph schema tab

Load the monolith's SDL (.graphqls, .graphql or .gql). Search its types and root methods, view each one's SDL, and copy a type as a federation @key stub. Under Assign to target domain / entity, click Save to record where the type or method moves, which tracks migration coverage. Unassign removes it.

Subgraphs tab

Review an imported subgraph: its operations (switch one between query and mutation, or delete it), its types, and the generated federated SDL. You can also rename or delete the subgraph here.

＋ Borrow / extend entity Subgraphs tab

Add a reference or extend stub for an entity owned by another subgraph, the same way as in the workbench's Subgraph SDL tab. Suggestions show the owning subgraph.

FedGQL subgraph tab

The exact registry rows the subgraph will produce, grouped by Entities, Schema, Queries and Mutations. Cells are editable and your edits are kept (Reset edits discards them). Rows that break the standards are highlighted, with the issue shown underneath. New rows start as Draft; set Approval to Proposed when a row is ready.

＋ Add type / query / mutation

Adds a row of your own to the subgraph, with an ID under the migration entity. ✕ removes a row you added.

Reset edits

Discards your cell edits and regenerates the rows from the imported spec.

Export subgraph / Export subgraph xls

Downloads <subgraph>-subgraph.xlsx with Entities, Schema, Queries and Mutations sheets laid out like the registry. Standards errors block the export; warnings ask you to confirm. Check that the EntityIDs match the registry before sharing it.

Copy to GQL Registry →

Checks the Proposed rows, together with the Entities rows they belong to, against the standards, then merges them into the registry on the GQL Registry tab. A row with the same ID is updated; any other row is added. Rows still in Draft are not copied.

GQL Registry tab

The Registry workbench, embedded in this page. It uses the same browser storage as workbench.html, so copied rows also appear there. Approve and export from it.

Code migration subgraph-codemigration.html

Generates the code that moves callers from REST to FedGQL. It opens on its own, or embedded in the Code migration tab of GQL migration.

Inputs

Load GQLRegistry.xlsx, which supplies the FedGQL operations and types, and the REST spec (OpenAPI or Swagger, in YAML or JSON). Pick the registry entity (subgraph) to limit the list to that subgraph's operations.

Load example header

Loads samples/GQLRegistry-sample.xlsx (including its pre-mapped BFF endpoints) with the REST spec picked in the dropdown. BFF opens BFF composite mode on POST /bff/checkout, the orchestrated checkout. A subgraph (e.g. cart) opens single-op mode on that subgraph, with REST and GraphQL operations already paired. Needs the pages served over http(s); on file:// use the Choose… buttons.

Mode

Single op maps one REST operation to one FedGQL operation. BFF composite maps one BFF endpoint to a set of FedGQL queries and mutations from different subgraphs.

Single op

Pick the REST operation and the GraphQL operation; they are paired automatically when an operation's Current Reference matches the REST method and path. Choose Client (JavaScript, Java, Android/Kotlin, iOS/Swift) or Server (Java Spring for GraphQL, .NET Hot Chocolate, Node.js Apollo Server). You get the REST and FedGQL versions side by side, with renamed fields and types highlighted, plus a sample response.

A sequence trace (Mermaid, rendered and copyable) shows how the router serves the operation: it calls the owning subgraph, then sends _entities calls by @key to every subgraph that owns an entity selected in the response. For example, cart → cart subgraph, then the product subgraph for each line's product fields. Mutations get the same trace.

BFF composite

Pick the BFF REST endpoint, then click ＋ Add FedGQL op for each operation it composes, and set an alias and arguments for each. The page generates:

  • the combined FedGQL document;
  • a single federated query, with a sequence diagram of how the router resolves the entity and then fetches from each subgraph by @key. When the owning entity is extended by another subgraph, the real contributed field is used (e.g. product { storeContext(storeId:) });
  • a mutation flow (see below), when the endpoint composes mutations;
  • the SDL for each subgraph involved;
  • BFF handler (server) or client code.

Mutation flow and the orchestrating mutation. The router runs root mutation fields one after another, but one field can't use the previous field's result. So a flow like checkout (read cart → check stock → take payment → clear cart) belongs inside one mutation's resolver: a saga or process coordinator.

  • Setting it up: under Orchestrating mutation, pick that mutation (e.g. submitCheckout). Every other op in the table becomes one of its steps, run in table order.
  • What you get:
    • the single mutation the client sends, with sample variables;
    • the ordered steps;
    • a Node.js orchestrator resolver skeleton, with a query/mutation document per step and compensation on failure;
    • a Mermaid sequence diagram of the orchestration.
  • Without an orchestrator: the diagram shows the router running the mutation fields in document order.
  • Saving it: the choice is saved in the BffMappings sheet as orchestrator.

Export registry + BFF mappings (.xlsx)

Writes the loaded registry back with a BffMappings sheet holding each endpoint's operations, aliases, arguments, order and owning operation. Load that workbook again later to restore the mappings.

FAQ & troubleshooting

Where is my data stored?

Each page caches its data in this browser's local storage. The Excel workbook is the only thing you share: export it, or push it to SharePoint or Google Drive. Clearing site data in the browser, or using a different browser, starts empty.

Files don't load automatically

When a page is opened straight from disk (file://), the browser blocks automatic loading. Use the file pickers, or serve the folder over http(s), for example with GitHub Pages or python3 -m http.server.

Copy to GQL Registry does nothing

Only Proposed rows are copied, and standards errors must be fixed first. Also make sure a registry entity is selected on Load data.

Excel warns about a value in a dropdown column

The exported dropdowns only warn. They accept values outside the list, so you can add a new persona or status and update the workbench to match later.
