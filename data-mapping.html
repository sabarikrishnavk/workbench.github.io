    Attribute lineage across layers

    One row per business term. Each column is a layer, from the core systems (MDM / PIM) through Kafka, the microservice's data and APIs to the UI. A cell lists the attributes in that layer tagged with the term. core → UI means the mappings connect a core-system attribute all the way to a UI attribute.     End-to-end traces

    Every mapping path from an attribute with no upstream source to one with no downstream target, with the transformation applied at each hop.

    Domains & applications

    Step 1: register every application under its domain. A domain, orchestrator or integration service owns its REST and GraphQL API, its database and the Kafka events it produces, so it is one application, not one entry per endpoint. Front ends integrate only through the BFF (REST) or the FedGQL router. Core and third-party systems feed an integration service through an API, a Kafka event or a CSV file.

    Integration flows

    Applications grouped by domain and joined by the flows that carry the mappings. Each edge label shows how the data crosses (REST API, GraphQL, Kafka event, File (CSV), CDC) and how many attribute mappings the flow carries.

    Flows

    Kafka event catalog (schema registry)

    Each event's topic, schema-registry subject, format, compatibility mode and partition key, plus who produces and consumes it. Each event belongs to the application that produces it: a core system (MDM CDC), an integration service or a domain service. Its attributes are mapped like any other dataset.

    Generate schema

    Builds a schema from a dataset's attributes. Dotted paths become nested records/objects and [] marks an array. Attributes that are not required become optional (an Avro ["null", T] union with a null default).
